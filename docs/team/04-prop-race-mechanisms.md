# 道具竞速赛 · 机制方案设计

> **规则**（PPT P9）：15 圈，可使用**最多 3 种机制**，每种**不超过 5 次**，
> 每次**不超过 3 秒**，**机制需绑定方向盘按键**。
> 说明原文：「附加题，发散思维，尽可能干扰对手 or 帮助自己」。

---

## 一、一个漂亮的对应关系

主办方的通信协议（`User/Bsp/ControlToCar.pb.h` → `CarData_Function`）里，
方向盘能下发的**布尔型按键字段正好是 3 个**：

| 协议字段 | 原设计用途 | 我们拿来做 |
|---|---|---|
| `c_signal` | 电容 / ERS 放电 | 机制 A |
| `battle_signal` | 缠斗 / DRS | 机制 B |
| `drift` | 漂移开关 | 机制 C |

**3 个 bool 按键 ↔ 规则允许的 3 种机制**，不需要改通信协议，也不需要主办方配合改地面站。
读法就是 `rc_ctrl.car_function.c_signal` 等，通信任务已经解析好了。

> ⚠️ **开营后必须确认的一件事**：方向盘上到底哪几个物理按键映射到这三个字段？
> 如果地面站现在把 `c_signal` 硬编码成 0（完整版固件的文档 §4.1 提到过这个情况），
> 那这条路就不通，要请主办方打开。**这个问题今天就要问。**

## 二、核心工程点：把规则写进固件

**不要靠车手手动松手来控制 3 秒。** 手一抖按成 3.2 秒就可能被判违规，
而且没人数得清用了几次。正确做法是写一个**机制管理器**，由固件强制保证：

- **上升沿触发** —— 按住不放只算一次，松开再按才是第二次
- **满 3 秒自动截断** —— 物理上不可能超时
- **每种用满 5 次后自动失效** —— 物理上不可能超次
- **冷却时间** —— 防手抖连点白白浪费次数
- **失联 / 低压时强制关闭** —— 安全兜底

这段代码本身就是很好的答辩材料：**「我们把比赛规则编译进了固件，所以我们不可能违规」**。

### 参考实现

放在 `chassis_task.c` 里，`Chassis_Loop()` 每 1ms 调用一次即可。

```c
/* ---- 道具赛机制管理器 ---- */
#define MECH_MAX_USE       5      /* 规则: 每种最多 5 次 */
#define MECH_MAX_MS     3000      /* 规则: 每次最长 3 秒 */
#define MECH_COOLDOWN_MS  500     /* 冷却, 防手抖连点浪费次数 */

typedef enum { MECH_BOOST = 0, MECH_TC, MECH_STROBE, MECH_COUNT } MechId_t;

typedef struct {
    uint8_t  active;         /* 当前是否生效 */
    uint8_t  used;           /* 已使用次数 */
    uint32_t start_tick;     /* 本次激活时刻 */
    uint32_t last_end_tick;  /* 上次结束时刻(冷却用) */
    uint8_t  key_prev;       /* 上一拍按键电平(上升沿检测用) */
} Mech_State_t;

static Mech_State_t mech[MECH_COUNT];

static void Mech_Update(MechId_t id, uint8_t key)
{
    Mech_State_t *m = &mech[id];
    uint32_t now = HAL_GetTick();

    /* 失联时一律强制关闭, 不允许任何机制残留 */
    if (rc_ctrl.RC_READY != 0)
    {
        if (m->active) { m->active = 0; m->last_end_tick = now; }
        m->key_prev = key;
        return;
    }

    if (m->active)
    {
        if (now - m->start_tick >= MECH_MAX_MS)      /* 到时自动截断 */
        {
            m->active = 0;
            m->last_end_tick = now;
        }
        else if (!key)                                /* 提前松手 */
        {
            m->active = 0;
            m->last_end_tick = now;
        }
    }
    else
    {
        /* 上升沿 + 还有次数 + 过了冷却 */
        if (key && !m->key_prev
            && m->used < MECH_MAX_USE
            && (now - m->last_end_tick) >= MECH_COOLDOWN_MS)
        {
            m->active     = 1;
            m->used++;
            m->start_tick = now;
            TIM4->CCR1 = BEEP_CCR;      /* 短鸣一声, 车手能听见"生效了" */
        }
    }
    m->key_prev = key;
}

/* 在 Chassis_Loop() 开头调用 */
static void Mech_Poll(void)
{
    Mech_Update(MECH_BOOST,  rc_ctrl.car_function.c_signal);
    Mech_Update(MECH_TC,     rc_ctrl.car_function.battle_signal);
    Mech_Update(MECH_STROBE, rc_ctrl.car_function.drift);
}
```

**次数复位**：每场比赛开始前要把 `used` 清零。三种做法，按优先级：
1. 地面站的 `rc_ctrl.car_status.race_mode` 有变化时清零（最干净，需确认地面站会不会发）
2. 板载按键 `PA1` 长按 2 秒清零（自己可控）
3. 每场比赛前重新上电（最笨但一定有效）

**车手反馈**：车就在同一个场地里，蜂鸣器是听得见的。约定：
激活时短鸣一声，第 5 次（最后一次）激活时鸣两声，用完后再按不响 —— 车手就知道没了。

## 三、三种机制的候选方案

按**实现风险**分三档。选择原则很重要：

> **道具赛只是四场比赛之一，而正赛和耐力赛是主分。**
> 任何会提高故障率的机制都是负收益 —— 一个卡住的机械挡板可能让你整场退赛。
> 建议配置：**2 个纯软件机制 + 最多 1 个硬件机制**。

### ✅ 机制 A：弹射起步 / Boost（自己增益）— 纯软件，强烈推荐

绑 `c_signal`。3 秒内：

- 强制解除档位限速（`gear_scale` 视为 1.0）
- `MOTOR_SLEW_PER_MS` 临时提高到 400（响应更快，代价是可能打滑）
- 油门系数 ×1.25，但 PWM 仍然硬限幅在 9999

**用途**：发车瞬间、长直道超车。

**必须带的保护**：电流冲击会把母线电压拉低，可能导致图传或主控重启（直接退赛）。
所以加一条：`if (chassis_measure.VBUS < 6.8f) 自动退出 Boost;`
这个细节写进报告很加分——说明你们真的想过副作用。

```c
if (mech[MECH_BOOST].active && chassis_measure.VBUS > 6.8f)
{
    ratio = ((fp32)throttle / 100.0f) * 1.25f;   /* 无视档位限速 */
    if (ratio > 1.0f) ratio = 1.0f;
}
```

### ✅ 机制 B：出弯循迹控制 TC（自己增益）— 纯软件，强烈推荐

绑 `battle_signal`。3 秒内检测驱动轮打滑并自动回油。

**打滑判据**（有编码器就能做）：油门在涨、PWM 在涨，但 `v_measure` 不涨甚至在抖 →
说明轮子在空转。此时把 PWM 乘 0.85，等速度重新跟上来再放开。

**用途**：出弯地板油。对手打滑空转的时候你在加速，一个弯就能拉开半个车身。

**为什么推荐**：纯软件、零硬件风险、真正有工程含量、答辩时好讲，
而且它用到了你们自己写的编码器测速——是整条电控链路的成果展示。

### ⚠️ 机制 C-1：爆闪干扰（干扰对手）— 需要额外硬件

绑 `drift`。3 秒内车尾大功率 LED 以约 10Hz 闪烁。

**原理**：所有人都是靠 FPV 摄像头驾驶的。摄像头有自动曝光，
被强光反复冲击时画面会一明一暗剧烈跳变，后车短时间内基本没法判断路线。
PPT 举例里写的「爆闪」应该就是指这个。

**实现**：不要用 GPIO 死循环翻转（会占 CPU），用一个 PWM 通道或在 1000Hz 循环里用时间戳翻转。

**需要的东西**：大功率 LED + MOSFET 驱动（板上小状态灯 PB8/PB9 亮度完全不够，
只能当指示，不能当武器）。这些**不在物资清单里，要申请或自备**。

> 🔴 **两个必须先问清楚的点**：
> 1. **会不会干扰计时？** 车顶那个红外传感器是比赛计时用的。如果 LED 有红外分量，
>    可能干扰自己或别人的计时系统 —— 那就不是「干扰对手」而是「破坏赛事设备」了。
>    **选纯可见光 LED，避开红外波段**，并且事先跟主办方确认。
> 2. **规则允许到什么程度？** 亮度有没有上限？直射对手算不算犯规？

### ⚠️ 机制 C-2：机械阻挡板（干扰对手）— 需要第二个舵机 + 今天就要建模

绑 `drift`。3 秒内舵机把一块挡板/扰流板展开，占据赛道内线宽度，逼后车减速或走外线。

**可行性（我查过工程了）**：
- 舵机配额是 **≤3 个**，转向只用了 1 个，**还有 2 个可用**
- 软件上：`TIM1_CH2/CH3/CH4`（PA9 / PA10 / PA11）目前**都没被占用**
  （USART1 没有初始化，TIM1 只配了 CH1），而且它们和转向舵机**共用同一个 50Hz 时基**，
  CCR 换算完全一样 —— 加第二个舵机在软件上几乎是免费的
- ⚠️ 但**必须确认这几个引脚在板子上有没有引出来**，这个只能看实物/原理图，我没法从代码判断

**🔴 时间敏感**：如果要做这个机制，**今天下午建模就必须预留第二个舵机的安装位和挡板的运动空间**。
明天再想加就来不及了 —— 底盘已经打印完了。**这是现在唯一需要立刻通知队友的事。**

### 其它可选（低成本备选）

- **鸣笛干扰**：蜂鸣器长鸣。零成本、零风险，但效果基本是心理层面的，建议只作为凑数的第三个机制。
- **假动作**：3 秒内故意让状态灯常亮，配合走位骗对手以为你要放大招。趣味性大于实用性。

## 四、推荐配置

| 机制 | 绑定按键 | 类型 | 硬件需求 | 风险 |
|---|---|---|---|---|
| A · 弹射起步 Boost | `c_signal` | 自己增益 | 无 | 低（带低压保护） |
| B · 出弯循迹控制 TC | `battle_signal` | 自己增益 | 无 | 无 |
| C · 爆闪 **或** 挡板 | `drift` | 干扰对手 | 有 | 中 |

**A 和 B 今晚就能写完并且不依赖任何硬件**，建议先把这两个做出来，
C 等确认了主办方的规则口径和硬件供应再定。
